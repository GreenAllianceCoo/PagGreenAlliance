## Resumen para el buzón

Se identificaron 8 necesidades del rediseño C+. Dos ya están cubiertas por el esquema actual (motivo de rechazo, y el resumen del asesor con conteos/último crédito). Tres tienen una solución de esquema clara y pequeña, y se proponen como migraciones nuevas sin aplicar: preferencia «avisarme» del sorteo, institución/estado activo en el carné, e historial + nota interna del admin. Y una — la fecha del primer descuento del embargo solidario, y en parte el estado «Desembolso» — depende de una decisión de negocio que no se debe inventar; queda como pregunta abierta (la de desembolso ya estaba registrada como P-47 en el plan).

## Migraciones propuestas (sin aplicar) y orden

Todas idempotentes donde fue posible (`add column if not exists`, `create or replace`, `drop trigger/policy if exists`, bloques `do $$ ... $$` con comprobación previa). Ninguna se aplicó; Sebas debe revisarlas y aplicarlas con `supabase db push` (o `apply_migration` vía MCP) después de correr una auditoría completa de `ga-auditor-supabase` con acceso a producción.

1. `20260925200000_perfiles_avisar_sorteo.sql` — columna de preferencia, independiente del resto.
2. `20260925200100_perfiles_institucion_y_activo.sql` — reemplaza `proteger_campos_perfil()`; aplicar después de la 1 (no depende de ella, pero mantiene el orden cronológico) y antes de cualquier cambio futuro a esa misma función.
3. `20260925200200_historial_y_notas_internas.sql` — tabla, triggers y función nuevos; no depende de las anteriores.
4. `20260925200300_realtime_admin_solicitudes.sql` — solo configuración de publicación; puede ir en cualquier momento, se puso al final porque es la de menor riesgo de esquema.
5. `20260925200400_indices_busqueda_admin.sql` — opcional, de rendimiento; sin prisa.

Ninguna de las 5 modifica una política ni una función que otra de las 5 también toque, salvo que la 2 reemplaza `proteger_campos_perfil()` por completo (como ya es costumbre en este repo cada vez que se agrega una columna protegida): si entre esta auditoría y el `db push` alguien más vuelve a tocar esa función, hay que fusionar a mano, no aplicar las dos versiones por separado.

## Sugerencias de pruebas para `ga-escritor-tests`

Si Sebas aplica las migraciones propuestas, valdría la pena automatizar (pgTAP, siguiendo el patrón de `supabase/tests/`):

- `perfiles_institucion_y_activo`: un asociado autenticado intenta `update perfiles set activo = false where id = auth.uid()` o `update perfiles set institucion = 'ejercito' where id = auth.uid()` → debe fallar con el mensaje del trigger; el mismo `update` hecho por un admin sobre la fila de otro debe pasar.
- `historial_solicitudes`: (a) un asociado autenticado hace `select * from historial_solicitudes` → 0 filas (RLS); (b) llama a `agregar_nota_solicitud(...)` → falla («Solo un administrador...»); (c) un admin la llama → inserta y la puede leer; (d) al aprobar/rechazar una `solicitudes_credito` (vía `update ... set estado = ...`), aparece sola una fila nueva en `historial_solicitudes` con `accion` igual al nuevo estado; (e) crear una solicitud de crédito o de afiliación genera la fila `accion = 'creada'`.
- `perfiles_avisar_sorteo`: el propio asociado puede prender/apagar `avisar_apertura_sorteo` en su fila; no puede cambiarla en la fila de otro (ya cubierto por la política general `perfiles_update`, pero vale la pena un caso explícito).
- Realtime (si Playwright/una prueba de integración lo permite): un cliente suscrito con el JWT de un asociado no recibe eventos de `solicitudes_credito` de otro asociado ni de `solicitudes_afiliacion` en absoluto; un cliente con JWT de admin sí recibe ambos.
